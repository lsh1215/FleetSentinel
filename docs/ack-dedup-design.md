# ack 프로토콜과 레코드 단위 dedup 설계

> 관련 문서 — [WAL 설계](wal-design.md)(축적 창을 닫는 쪽) · [시스템 설계](sdd.md) S-7 ·
> [수집 계층 설계 검토](ingestion-design-review.md) §4.8 · 데이터 사실은
> [데이터 설계](data-design.md)에만 있다

## 1. 개요

[WAL](wal-design.md)이 **차량 안에서** 유실을 막았다. 남은 것은 **차량 밖**이다 — 보낸
레코드가 정말 도착했는지 어떻게 아는가, 그리고 다시 보낸 레코드가 두 번 저장되지 않게
어떻게 막는가.

이 둘은 별개 문제처럼 보이지만 **한 문제의 양면**이다.

```
전송을 exactly-once로 만들려면          →  분산 트랜잭션(2PC)이 필요하다
                                          가용성을 포기하고 지연을 늘린다
전송은 at-least-once로 두고             →  실패하면 그냥 다시 보낸다
저장 지점에서 멱등하게 흡수하면          →  결과가 exactly-once가 된다
```

아래 것을 택한다. 그래서 **ack은 "다시 보내도 되는 지점"을 정하는 프로토콜**이고,
**dedup은 "다시 온 것을 흡수하는 장치"** 다. 하나가 없으면 다른 하나가 무의미하다.

* ack이 없으면 → 언제 WAL을 비워도 되는지 모른다 → 디스크가 찬다
* dedup이 없으면 → ack이 유실될 때마다 데이터가 중복 저장된다

`seq`를 도입하면 두 번째가 **극적으로 싸진다**. 그게 이 문서의 핵심이다 —
`event_id` 집합으로 124.8 GB 쓰던 상태가 **350 KB**가 된다(§4.2 실측).

## 2. 핵심 요구사항 및 문제상황

### 2.1 요구사항

| # | 요구사항 |
|---|---|
| **A-1** | ack된 레코드는 **정말로** 안전해야 한다 — ack 후 어느 컴포넌트가 죽어도 살아남는다 |
| **A-2** | ack 트래픽이 데이터 트래픽에 비례해서는 안 된다 |
| **A-3** | 저부하에서도 ack이 전진해야 한다 — 커밋이 멈추면 WAL이 자란다 |
| **A-4** | 게이트웨이는 **stateless**를 유지한다 |
| **D-1** | 중복은 반드시 걸러진다 — 저장 계층에 두 번 들어가지 않는다 |
| **D-2** | 순서가 뒤바뀐 도착은 **유실이 아니다** |
| **D-3** | dedup 상태가 **데이터 양에 비례해 자라지 않는다** |
| **D-4** | 유실이 생기면 **탐지된다** — 조용히 사라지지 않는다 |

A-4가 제약이다. 게이트웨이 stateless는 gRPC를 택한 결정적 근거였고
([설계 검토](ingestion-design-review.md) §4.8) 여기서 깨면 그 결정이 무너진다.

### 2.2 문제상황

#### P-A1. gRPC 스트림에는 애플리케이션 수준 ack이 없다

HTTP/2 흐름 제어(`WINDOW_UPDATE`)는 **바이트가 상대 버퍼에 들어갔다**를 말한다. 그건
"게이트웨이가 Kafka에 안전하게 넣었다"와 다르다. gRPC 단방향 스트림에서 `SendMsg`가
성공해도 서버가 그 메시지를 처리했다는 보장은 없다. 그래서 **응답 스트림으로 직접
ack을 만들어야 한다.**

> MQTT를 쓴다면 QoS 1의 `PUBACK`이 있다. 그러나 그건 **브로커까지의 홉**만 보장한다.
> 브로커→Kafka 브리지에서 잃으면 차량은 모른다. 우리 `seq` ack은 **Kafka 쓰기 성공까지**
> 를 덮는 종단 보장이다 — 홉 단위 보장과 종단 보장은 다른 물건이다.

#### P-A2. 언제 ack하는가 — 잘못 정하면 조용히 잃는다

```
수신 직후 ack   →  게이트웨이가 Kafka에 쓰기 전에 죽는다
                   차량은 ack을 받았으니 WAL에서 지운다
                   ⇒ 아무도 그 레코드가 있었다는 사실을 모른다
```

이건 결번도 남기지 않는다. 차량 쪽 `seq`는 연속이고 Kafka 쪽에는 애초에 안 들어갔으므로
**"내가 보낸 것"과 "저장된 것"을 대사하지 않으면 영원히 모른다.**

#### P-A3. 매 레코드 ack은 낭비다

차량당 1,295 rec/s([데이터 설계](data-design.md) §4.4)에서 500대면 **647,500 ack/s**다.
ack 하나가 수십 바이트라도 되돌아오는 트래픽과 처리 비용이 무시할 수 없다.

#### P-A4. 재개 지점을 누가 아는가

재연결 시 어디서부터 다시 보낼지 정해야 한다. "서버가 마지막으로 본 `seq`를 알려준다"가
자연스럽지만 그러면 **게이트웨이가 차량별 상태를 들어야 한다**(A-4 위반). 게이트웨이가
수십 대로 오토스케일하는데 어느 인스턴스에 붙어도 같은 답을 줘야 한다면 공유 저장소가
필요해지고, 그건 stateless가 아니다.

#### P-D1. `event_id` 집합은 데이터 양에 비례해 자란다

레코드마다 UUID/ULID를 달고 "이미 본 id 집합"으로 거르면 상태가
**초당 레코드 수 × TTL** 이다.

| TTL | id 수 (500대) | 상태 |
|---|---|---|
| 10분 | 388M | **41.6 GB** |
| 30분 | 1,166M | **124.8 GB** |

(실측 id당 115 B — §4.2) TTL을 줄이면 상태는 줄지만 **재전송 지연이 TTL을 넘으면 중복이
새어나간다.** 차량이 30분간 터널·음영 지역에 있다가 복귀하면 정확히 그 일이 생긴다.
즉 TTL은 자유롭게 줄일 수 있는 값이 아니다.

#### P-D2. `last_seen` 정수 하나로는 순서 역전을 유실로 만든다

`seq <= last_seen` 이면 중복이라고 판정하면, **늦게 도착한 새 레코드를 버린다.** 순서
역전이 실제로 생기는 경로:

| 경로 | 왜 생기는가 |
|---|---|
| Kafka 파티션 수 변경 | 같은 `vehicle_id`가 다른 파티션으로 이동 — 파티션 간 순서 보장은 없다 |
| 스트림 중복 | 재연결 경합·로드밸런서 재시도로 두 게이트웨이가 같은 파티션에 인터리빙 |
| 재전송과 신규의 교차 | 재전송분이 네트워크에서 지체되는 동안 신규분이 먼저 도착 |

그리고 이 유실은 **탐지되지 않는다** — dedup이 "중복을 잘 걸렀다"고 보고하기 때문이다.
D-1을 지키려다 D-2를 깨는 것이고, 둘 중 더 위험한 쪽을 깨는 것이다.

#### P-D3. WAL이 사라지면 `seq`가 0으로 돌아간다

`seq`는 WAL이 발급한다(WAL 설계 §3.1). SD카드 교체·초기화·차량 소프트웨어 재설치로
로그가 사라지면 `seq`가 0부터 다시 시작한다. `last_seen`이 이미 크면:

```
last_seen = 1,200,000
새 레코드   seq = 0, 1, 2, ...    →  전부 "중복"으로 판정  →  전량 유실
```

**차량 한 대가 영구히 침묵한다.** 그리고 유실이 아니라 "중복이 많다"로 보인다.

#### P-D4. 유실을 탐지할 방법이 없다 ([SDD](sdd.md) L-12)

`event_id`는 **유일성**을 준다. 유실 탐지에 필요한 건 **연속성**이다. 하나가 없어졌을 때
없어졌다는 사실 자체를 모른다. 재생기에서는 발행 집합을 알아서 대사할 수 있지만, 실차량
경로에서는 "차량이 무엇을 보냈는지"의 진실이 차량 안에만 있다.

## 3. 해결방법 및 구현 방식

### 3.1 ack은 Kafka 쓰기 성공 후에만 나간다 (A-1, P-A2)

```
게이트웨이:  gRPC 수신 → Kafka produce(acks=all) → 성공 콜백 → 이때 완료 표시
                                                              ↑
                                            여기보다 앞에서 ack하면 P-A2
```

`acks=all`은 모든 in-sync replica가 썼다는 뜻이다. 그 콜백 이후에만 그 `seq`를
"완료"로 표시한다. **게이트웨이가 죽으면 ack이 안 나가고, 차량은 재전송한다** — 그게
정상 동작이다.

### 3.2 Cumulative Acknowledgement (CACK) — 그게 정확히 성립하는 이유 (A-2)

ack은 **"이 `seq` 이하는 전부 안전하다"** 하나의 정수다. 구간 목록(SACK 방식)이 아니다.
TCP가 쓰는 방식과 같고 **Cumulative Acknowledgement(CACK)** 라 한다. 이하 CACK으로 쓴다.
그게 성립하려면 완료가 순서대로 와야 하는데, 실제로 그렇다:

1. Kafka producer 콜백은 **파티션별로 순서대로** 호출된다 (문서화된 보장)
2. 파티션 키가 `vehicle_id`이므로 한 차량의 레코드는 **한 파티션**에 간다
3. `enable.idempotence=true` 면 `max.in.flight.requests.per.connection <= 5` 에서도
   Kafka가 시퀀스 번호로 재정렬한다 — **처리량을 포기하지 않고** 순서가 유지된다

3번이 중요하다. 순서 보장을 얻으려고 `max.in.flight=1`로 내리면 처리량이 무너지는데,
멱등 프로듀서는 그 대가 없이 순서를 준다.

그래도 `AckTracker`는 **순서 없는 완료를 받아낸다**. 위 보장에 의존하지 않는 편이 안전하고
비용이 없다(정수 집합 하나). 구멍이 있으면 그 아래까지만 ack한다:

```
완료: 0, 1, 3, 4, 5        →  ack_seq = 1     (2가 안 끝났다)
완료: 2                    →  ack_seq = 5     (한 번에 전진)
```

### 3.3 CACK 방출 주기 — 개수 또는 시간, 먼저 오는 것 (A-2, A-3)

| 조건 | 값 | 이유 |
|---|---|---|
| 개수 | 128 레코드 | 1,295 rec/s에서 약 99ms — 차량당 10 ack/s |
| 시간 | 200 ms | 저부하(정차·시동 대기)에서도 커밋이 전진한다 |

**개수 조건만 두면 A-3을 위반한다.** 차량이 초당 5레코드만 보내면 128개가 모이는 데
26초가 걸리고, 그 동안 WAL이 자라고 커밋이 멈춘다.

전진하지 않은 ack은 **다시 방출하지 않는다** — 같은 값을 반복해 보낼 이유가 없다.

### 3.4 재개 지점은 클라이언트가 정한다 (A-4, P-A4)

```
차량:      WAL 커밋 지점 + 1 부터 재전송        ← 진실은 차량 안에 있다
게이트웨이: 받은 걸 그대로 Kafka에 넣는다        ← 상태 없음
Flink:     이미 본 것은 dedup이 버린다          ← 중복 흡수
```

이미 Kafka에 들어갔지만 ack이 유실된 구간이 다시 온다. **의도된 중복**이다. 대가로
얻는 것:

* 게이트웨이가 차량별 상태를 안 든다 → 오토스케일·무중단 배포가 자유롭다
* 재개 협상 왕복(round trip)이 없다 → 재연결이 빠르다
* 게이트웨이 인스턴스가 바뀌어도 동작이 같다

### 3.5 dedup 키는 `(vehicle_id, boot_id, seq)` (D-3, P-D3)

`seq`가 차량별로 단조 증가하면 "어디까지 봤는가"를 정수로 들면 된다. 상태가
**차량 수**에 비례하고 **데이터 양과 무관**해진다.

`boot_id`는 P-D3을 닫는다. WAL 디렉터리 생성 시 UUID를 발급해 파일로 보존하므로,
로그가 사라지면 값이 바뀐다. dedup은 `boot_id`가 달라진 것을 보고 **상태를 리셋**한다.

```python
if st.boot_id != boot_id:          # WAL이 사라졌다
    st.last_seen = st.contiguous = seq - 1
    st.bits = bytearray(...)       # 이전 생애의 판정을 끌고 오지 않는다
```

`boot_id`는 스트림 헤더에서 한 번 보내므로 레코드마다 실리지 않는다.

### 3.6 슬라이딩 윈도우 비트맵 — 순서 역전을 흡수한다 (D-2, P-D2)

`last_seen` 하나가 아니라 **최근 W개 구간의 도착 여부 비트맵**을 둔다. TCP SACK과 같은
구조다. 비트맵은 `seq % W`로 인덱싱하는 **환형 버퍼**여서, 윈도우가 전진할 때 비트를
옮기지 않고 **새로 들어오는 슬롯만 비운다**.

```
seq > last_seen            →  윈도우 전진, 수락
last_seen-W < seq <= last_seen
    비트 1                 →  중복, 거부
    비트 0                 →  지각 도착한 새 레코드, 수락      ← 정수 하나면 버렸을 것
seq <= last_seen - W       →  윈도우 밖. 거부하되 따로 계수한다
```

마지막 줄이 이 설계의 유일한 유실 경로다. **`too_old` 카운터로 분리해서 센다** —
`duplicate`와 섞어버리면 "중복을 잘 걸렀다"로 보여서 조용히 지나간다.

W = 4,096이면 1,295 rec/s에서 **약 3.2초** 분량, 비트맵 **512 B/차량**이다. 3.2초를
넘겨 도착한 레코드가 새 것일 상황이면 이미 다른 문제가 있다는 신호다.

### 3.7 유실이 관측 가능해진다 (D-4, P-D4)

비트맵이 있으면 **구멍 없이 연속으로 받은 최고 `seq`** 를 계산할 수 있다.

```
last_seen   = 지금까지 본 가장 큰 seq
contiguous  = 그 아래에 구멍이 하나도 없는 최고 seq
```

`last_seen - contiguous`가 미결 구간이다. 구멍이 지각 도착으로 메워지면 `contiguous`가
따라 올라간다. **메워지지 않고 윈도우 밖으로 밀려나면 그 순간 유실로 확정한다.**

구현의 요점은 **비우기 전에 읽는 것**이다. 슬롯 `n % W`는 전진 직전까지 `n - W`를 담고
있으므로, 그 슬롯을 비우기 전에 비트를 보면 `n - W`가 도착했는지 알 수 있다.

```python
for n in range(prev + 1, end + 1):
    old = n - self.window
    if old > st.contiguous:
        if not self._test(st, old):    # old와 n은 같은 슬롯이다
            st.lost += 1               # 회복 불가로 확정
        st.contiguous = old
    self._clear(st, n)
```

이게 **L-12를 닫는다** — 유실 판정이 "발행 집합을 아는 재생"에서만 되던 것에서
**운영 중 스트림에서 차량별로** 되는 것으로 바뀐다. 그리고 `contiguous`는
[WAL 설계](wal-design.md) §3.6의 "버린 `seq` 구간"과 대사할 수 있다.

### 3.8 `event_id`를 제거하고 `(vehicle_id, boot_id, seq)`를 자연 키로 쓴다

`event_id`(ULID)의 용도가 셋이었는데 전부 대체된다.

| 용도 | 대체 |
|---|---|
| dedup 키 | `(vehicle_id, boot_id, seq)` — §3.5 |
| 저장 계층 멱등 upsert 키 | 같은 3튜플. **정렬 가능**하므로 오히려 낫다 |
| 로그에서 레코드 추적 | 같은 3튜플. "3번 차량 boot-a의 40,921번"이 UUID보다 읽기 쉽다 |

부수 효과로 페이로드가 줄고 UUID 생성 비용(647k/s)이 없어진다. ULID 26자를 varint
`seq`로 바꾸면 레코드당 **약 22 B, 342 B의 6.4%** 다.

`boot_id`는 레코드가 아니라 **스트림 헤더**에 실린다.

### 3.9 dedup은 게이트웨이가 아니라 Flink에서 돈다

| 위치 | 문제 |
|---|---|
| 게이트웨이 | 상태가 8 B/차량이라도 **stateless가 깨진다**(A-4). 죽으면 상태를 잃고 중복이 그대로 Kafka로 새어나간다 |
| **Flink** | keyed state가 **체크포인트로 복구된다**. `keyBy(vehicle_id)`가 상태를 자연스럽게 분산한다 |

Flink가 맞다. `keyBy(vehicle_id)`는 Kafka 파티셔닝과 이미 일치하므로(파티션 키가
`vehicle_id`) **셔플 없이** 로컬 상태로 처리된다.

상태 TTL은 이제 **본질적이지 않다** — 상태가 차량 수에 비례하고 차량 수는 유한하기
때문이다. `event_id` 방식에서 TTL이 상태 크기를 지배하던 것과 결정적으로 다르다.
차량이 은퇴할 때만 상태를 버린다.

### 3.10 커밋 포인터가 durable 지점을 앞지를 수 있다 — `seq` 재사용 방지

**구현 중에 발견한 문제다.** 배송기는 아직 fsync되지 않은 레코드도 보낼 수 있다. 그
자체는 안전하다(이미 Kafka에 있으므로). 그런데 그 ack으로 **커밋 포인터가 WAL의 durable
지점을 앞지를 수 있다.** 전원이 끊기면:

```
COMMIT 파일:       500  (fsync됨)
세그먼트 durable:  100  (그 위는 페이지 캐시에서 사라졌다)
복구 후 next_seq:  101  ← seq 101..500을 재사용한다
```

재사용된 `seq`는 하류에서 **중복으로 판정돼 버려진다.** 결번이 없으므로
`contiguous`도 정상으로 보인다 — **탐지되지 않는 유실**이고, 그래서 보통의 유실보다
나쁘다.

해법은 복구 시 커밋 포인터를 하한으로 쓰는 것이다.

```python
floor = self.committed_seq + 1
...
return max(last_seq + 1, floor)
```

### 3.11 배송기는 커서를 들어야 한다 — 2차식 회피

**역시 구현 중에 발견했다.** `Wal.read_from()`은 호출마다 세그먼트를 `read_bytes()`로
통째로 읽는다. 복구·검증 경로에는 맞지만 배송기는 배치마다 부르므로, 4 MB 세그먼트
하나를 배송하는 동안 같은 4 MB를 수십 번 다시 읽는다.

실측 처리량이 **43,984 → 16,587 rec/s** 로 떨어졌다. `WalCursor`가 `(세그먼트, 오프셋)`을
들고 이어 읽도록 바꿔 회복했다. 파일 핸들은 붙들지 않는다 — **커밋이 세그먼트를
삭제하므로** 열어둔 핸들은 지워진 inode를 가리킬 수 있다.

### 3.12 역압 — ack이 멈추면 창이 닫힌다

```
보낼 수 있는 상한 = max_inflight - (미ack 레코드 수)
```

ack이 오지 않으면 창이 닫히고 그 시점부터 WAL이 자란다. **역압이 네트워크에서 디스크로
흡수된다.** 디스크 상한에 닿으면 오래된 세그먼트를 버리고([WAL 설계](wal-design.md) §3.6)
버린 `seq` 구간을 기록한다 — §3.7의 `lost`와 대사되는 유실이다.

> 병렬도를 올리면 선형으로 늘어난다. 그리고 실제 구현은 JVM이다. 이 수치는 속도보다

### 4.6 핵심 검증 — SIGKILL 후에도 하류가 보는 것은 정확히 한 번

별도 프로세스가 WAL에 쓰면서 배송하는 중에 **SIGKILL**하고, 재시작해 이어서 배송한 뒤,
게이트웨이 로그를 dedup에 통과시켜 **하류가 실제로 보는 것**을 재현한다.

재전송량을 우연에 맡기지 않고 **예측해서 확인한다**:

```python
max_logged = max(seq for ... in raw_before)        # 게이트웨이에 들어간 최고 seq
committed_at_kill = Wal(wal_dir).committed_seq     # 차량이 커밋한 지점
expected_dup = max_logged - committed_at_kill      # 재전송될 구간

assert len(raw) - len(accepted) == expected_dup    # 재전송량이 예측과 일치
assert seqs == list(range(len(seqs)))              # 결번이 있다 = 유실
assert all(p == payload_for(s) for s, p in accepted)  # 페이로드 정렬
assert d.stats().lost == 0 and d.stats().too_old == 0
```

`expected_dup`을 계산해서 맞추는 것이 중요하다. "중복이 있었다"만 확인하면 죽는 시점에
따라 0이 되어 **재전송 경로를 안 타고도 통과**한다.

## 5. 한계

| # | 한계 |
|---|---|
| **A-L1** | **스트림 fencing이 없다.** 같은 차량이 두 스트림을 동시에 열면 두 게이트웨이가 같은 파티션에 인터리빙하고, 앞선 스트림의 `seq`가 뒤처진 스트림의 것을 윈도우 밖으로 밀어낼 수 있다. 비트맵이 완화하지만 닫지는 못한다. 제대로 닫으려면 **단조 증가하는 스트림 세대(epoch)** 로 낡은 스트림을 거절해야 하는데, `boot_id`가 UUID라 순서가 없어 그대로는 쓸 수 없다 |
| **A-L2** | **윈도우 밖 지각 도착은 유실이다.** §3.6의 `too_old`. W=4,096은 3.2초이고, 그보다 긴 역전이 실제로 생기는 환경(파티션 재배치 중)에서는 W를 키워야 한다 — 비용은 차량당 선형이다 |
| **A-L3** | **첫 레코드 아래는 검사할 수 없다.** 차량의 첫 관측 `seq`가 1,000이면 0..999가 있었는지 알 방법이 없어 정상이라고 가정한다. Flink 상태가 체크포인트에서 복구되지 않은 경우에만 해당한다 |
| **A-L4** | **`boot_id` 인터리빙.** 구 세션 재전송과 신 세션이 겹치면 서로 리셋을 유발해 중복이 통과할 수 있다. 중복 통과는 유실보다 낫지만 완전하지 않다 |
| **A-L5** | **Kafka 콜백 순서 보장에 기대는 부분이 있다.** `AckTracker`는 순서 없는 완료를 받아내지만(§3.2), CACK 자체가 "그 아래는 전부 갔다"는 의미이므로 **한 차량이 여러 파티션에 걸치면** 성립하지 않는다. 파티션 키를 `vehicle_id`로 고정하는 것이 전제다 |
| **A-L6** | **실차량에는 없다.** 재생기에서 검증했고 온보드 소프트웨어는 [SDD](sdd.md) L-2 범위 밖이다. SIGKILL은 **프로세스 종료**를 재현하며 전원 손실 창(WAL 그룹 커밋 10ms)은 남는다 |
| **A-L7** | **Flink 상태 백엔드 실측이 없다.** 350 KB는 Python 프로세스 메모리다. RocksDB 상태 백엔드에서 체크포인트 크기·복구 시간은 측정하지 않았다 |
