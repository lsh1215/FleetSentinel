## 1. 해당 없음 — 이미 결정됐거나 스코프 밖

| 지적 | 왜 해당 없나 |
|---|---|
| **LiDAR raw를 MQTT로 보내면 안 된다** | 우리는 보내지 않는다. Claim-Check로 원시 센서는 HTTPS→오브젝트 스토리지다(SDD §3 S-1). 일반 원칙으로는 맞지만 **설계의 출발점이 이미 그것이었다** |
| `max_packet_size` 초과 (수백 KB~MB) | MQTT 메시지가 43 KB다 |
| 드라이버 링버퍼 오버런 | 온보드 소프트웨어. SDD §4.2 **L-2에 "구현하지 않는다"** 로 등재됨 |
| 센서 콜백 스레드 블로킹 | 같은 이유 |
| QoS 2는 고주파에 부적합 | QoS 1 전제. QoS 2를 검토한 적 없다 |
| GC pause | Flink는 체크포인트로 흡수. 브리지는 §4.4 참조 |

## 2. 이미 해결돼 있던 것

| 지적 | 우리 상태 |
|---|---|
| 센서 타임스탬프를 페이로드에 넣어야 | ✅ **타임스탬프 3종** 계약([데이터 설계 §5](data-design.md)) |
| 토픽 간 순서 보장 없음 | ✅ 키프레임(2Hz)을 동기화 앵커로 이미 지정 |
| QoS 1 중복 → dedup 필요 | ✅ [잠정 노트 §6-1](pipeline-notes-provisional.md)에 설계 |

## 4. 개선점

### 4.1 ⚠️ 애플리케이션 배치가 설계 원칙을 어겼다 (가장 심각)

**100ms 배치는 원천이 그렇게 주는 게 아니다.** nuScenes는 개별 레코드를 네이티브 주기로 준다
(`zoesensors` 937Hz, `ms_imu` 97Hz, `ego_pose` 19.5Hz 등, 합 1,295 rec/s). 배치는 **전송
효율을 위해 우리가 넣은 것**이다.

**두 종류의 배치를 구분하지 못한 것이 잘못이었다.**

| | **애플리케이션 배치** (기존 설계) | **전송 계층 배치** (Kafka 프로듀서·TCP) |
|---|---|---|
| 배치가 보이는 곳 | **데이터 계약** (`SignalBatch` 스키마) | 보이지 않는다. 계약은 레코드 단위 |
| 실패 단위 | **배치 132건 통째** | 레코드 (프로듀서가 시퀀스로 추적·재시도) |
| 메모리 유실 창 | **100ms** | `linger.ms` (보통 5~10ms) |
| dedup 단위 | 배치 | **레코드** |
| 관측되는 처리량 | 9.8 msg/s — **문제가 숨는다** | 1,295 rec/s — **문제가 보인다** |

**"배치로 처리하는 건 유실에 가깝다"는 지적이 맞다.** 배치는 레코드를 버리지 않지만:

- 실패 입도가 **1건 → 132건**으로 거칠어진다
- 창이 닫히기 전에 프로세스가 죽으면 **최대 100ms분이 메모리에서 사라진다**
- 그리고 **어려운 문제가 숫자에서 사라진다.** 1,295 rec/s가 9.8 msg/s로 보이면 처리량 설계의
  근거 자체가 흐려진다

**왜 그랬나 — MQTT의 구조적 제약 때문이다.**

MQTT는 PUBLISH 하나 = 페이로드 하나이고 **프로토콜 수준 배치가 없다.** 그래서 1,295 rec/s를
보내려면 초당 1,295 PUBLISH를 해야 하는데, in-flight window가 상한을 만든다.

| RTT | 상한 (`max_inflight=20`) | 필요 | 판정 |
|---|---|---|---|
| 50 ms | 400 msg/s | 1,295 | ❌ **불가** |
| 20 ms | 1,000 msg/s | 1,295 | ❌ **불가** |
| 10 ms | 2,000 msg/s | 1,295 | ⚠️ 여유 1.5배 (셀룰러에서 비현실적) |

**MQTT로는 레코드 단위 전송이 물리적으로 안 된다.** `max_inflight`를 올려도 미확인 메시지가
쌓이는 것이라 브로커 메모리와 재전송 폭풍으로 옮겨가는 문제다.

> **그러므로 결론은 "배치를 유지한다"가 아니라 "신호 경로에 MQTT가 틀렸다"다.**
> MQTT가 애플리케이션 배치를 강제하고, 그 배치가 실패 입도를 거칠게 만들고 문제를 숨긴다.
> 원인을 고쳐야 한다.

**수정 — 프로토콜을 발생률로 나눈다**

| 경로 | 발생률 | 프로토콜 | 배치 |
|---|---|---|---|
| ① 신호 | **1,295 rec/s** | **Kafka 프로듀서 직접** | 전송 계층 (`linger.ms`) |
| ② 인지 산출 | 2.1 msg/s | 같이 | — |
| ③ 원시 센서 | 클립당 1건 | HTTPS resumable | — |
| `segment-ref` · 차량 상태 · heartbeat · (장래) 명령 | 저주파 | **MQTT** | — |

**MQTT는 저주파 채널만 담당한다.** 그게 원래 설계 의도에 맞는 용도이고, LWT로 차량 오프라인을
즉시 검출하는 장점도 그대로 남는다.

**Kafka 프로듀서가 주는 것** — 멱등 프로듀서(`enable.idempotence=true`)가 **레코드 단위 시퀀스
번호로 중복·순서를 브로커까지 보장**한다. 전송 계층에서 배치가 일어나지만 계약은 레코드
단위로 유지되고, 실패 시 프로듀서가 재시도하므로 유실 창이 `linger.ms`로 줄어든다.

**대안 — gRPC 스트림 + 게이트웨이**: 차량이 gRPC로 게이트웨이에 보내고 게이트웨이가 Kafka에
쓴다. HTTP/2 flow control이 있고 차량 클라이언트가 가볍다. 다만 **게이트웨이가 브리지와 같은
문제를 그대로 갖는다**(§4.4). 홉이 하나 줄어드는 Kafka 직접이 단순하다.

**정직한 한계**: 실제 차량이 셀룰러로 Kafka 클라이언트를 돌리는 건 흔하지 않다. 실무는 MQTT나
자체 HTTP/gRPC 업링크를 쓴다. 우리가 Kafka 직접을 택하는 이유는 **레코드 단위 계약을 지키면서
멱등 보장을 얻는 가장 단순한 경로**이기 때문이고, 이건 트레이드오프다.

**더 근본적인 트레이드오프** — 1,295 rec/s가 전송을 어렵게 만드는 근원은
[다운샘플하지 않기로 한 결정](pipeline-notes-provisional.md)이다. 실제 fleet은 온보드에서
집계·다운샘플한다. 우리는 무손실을 택했고, 그 대가가 전송 난이도다. **배치로 그 대가를
안 내는 척한 것이 잘못이었다.**

### 4.2 ⚠️ 유실 탐지 수단이 없다

"유실 0"은 이 프로젝트의 핵심 주장이고 `event_id` 집합 대사로 증명한다. 그런데 **그 증명은
재생에서만 성립한다** — 우리가 무엇을 발행했는지 알기 때문이다.

**실차량 경로에서는 전송 계층이 조용히 버리면 그것이 존재했다는 사실 자체를 모른다.**

배치 봉투의 `window_start`가 순번 역할을 할 것 같지만 안 된다.

```
정상      ... 12300, 12400, 12500 ...
유실      ... 12300,        12500 ...   ← 12400이 없다
무데이터   ... 12300,        12500 ...   ← 12400에 레코드가 없었다
```

**둘이 구별되지 않는다.** 정차 중이면 창이 빌 수 있다.

**수정** — 차량별 **단조 순번(`seq`)** 을 페이로드에 넣는다. 레코드 단위 전송으로 바꾸면
`(vehicle_id, channel, seq)` 조합이고, 소비자가 결번을 보고 유실을 **탐지**할 수 있다.

`event_id`(ULID)는 유일성·멱등성을 주지만 **연속성을 주지 않는다.** 두 필드는 역할이 다르다.

| 필드 | 역할 |
|---|---|
| `event_id` | 멱등키 — 같은 것을 두 번 처리하지 않는다 |
| **`seq`** | **연속성** — 빠진 것을 알아낸다 |

### 4.3 ⚠️ 브로커 큐 기본값이 fleet 규모에서 1초를 못 담는다

MQTT를 저주파 채널로 좁히면 완화되지만, 그 채널에도 적용된다.

| N(차량) | 유입 (신호 포함 기준) | 큐 1000건 = |
|---|---|---|
| 10 | 119 msg/s | 8.4초 |
| 100 | 1,190 msg/s | **0.84초** |
| 500 | 5,950 msg/s | **0.17초** |

**소비자가 0.8초만 멈춰도 조용히 버려진다.** 기본값을 그대로 쓰면 안 된다.

**수정** — `max_queued_messages`·`max_queued_bytes`·overflow 정책을 명시하고, **큐 깊이를
관측 지표에 추가**한다(SDD §6.2에 현재 없다). 조용히 버려지는 것을 알 수 있어야 한다.

### 4.4 ⚠️ 브리지·게이트웨이 계층이 설계에 없다

다이어그램에 `MQTT → 브리지 → Kafka`를 그려놓고 설계하지 않았다. 신호를 Kafka 직접으로
바꾸면 신호 경로에서는 사라지지만, **저주파 MQTT 채널에는 여전히 필요하다.**

정해야 할 것:

| 결정 | 선택지 | 판단 |
|---|---|---|
| ack 순서 | MQTT ack를 Kafka 쓰기 **전** vs **후** | **후**가 맞다. 전이면 유실, 후면 중복 — 중복은 dedup이 흡수한다 |
| 실패 처리 | Kafka 쓰기 실패 시 재시도 / DLQ | 재시도 후 상한 초과 시 DLQ |
| 백프레셔 | 브리지가 느려지면 | MQTT ack를 늦춰 브로커 큐로 역전파 → §4.3 관측 필요 |
| 프로세스 종료 | in-flight 메시지 | MQTT ack 전이면 재전송된다(중복 허용 설계와 정합) |

### 4.5 ⚠️ MQTT 버전과 세션 정책이 미결정

문서에 "MQTT"라고만 적혀 있다.

| 결정 | 근거 |
|---|---|
| **MQTT 5.0 채택** | Receive Maximum(명시적 flow control), Response Topic(장래 명령), Session Expiry가 모두 5.0 기능. 3.1.1이면 flow control이 브로커 구현에 종속된다 |
| **`clean_session=false`** + 세션 만료 | true면 재연결 시 큐가 통째로 소실된다. 셀룰러 단절을 전제한 설계라면 false여야 한다 |
| **keepalive 값** | 재연결 구간 손실 폭을 결정한다. 짧으면 오탐, 길면 검출 지연 |

## 4.6 층위를 나누지 않아 후보 비교가 성립하지 않았다

"Kafka vs gRPC vs Pub/Sub vs MQTT" 중 무엇을 쓸지 고민했는데, **네 후보가 같은 층위가
아니다.** 그래서 나란히 놓고 비교하면 답이 안 나온다.

```
차량 ──[① 업링크 프로토콜]──▶ 수집 게이트웨이 ──[② 클라우드 버스]──▶ Flink
      MQTT · gRPC · HTTPS                        Kafka · Pub/Sub
      WAN · 신뢰 불가 클라이언트                     VPC 내부 · 신뢰 경계 안
```

| 후보 | 층위 |
|---|---|
| MQTT · gRPC · HTTPS | ① 업링크 |
| Kafka · Pub/Sub | ② 내부 버스 |

**Kafka↔Pub/Sub가 대안이고 MQTT↔gRPC가 대안이다.** 둘은 같이 쓰는 것이 정상이다.

**그리고 ①②는 반드시 분리된다** — 선택이 아니라 구조다. 내부 버스를 인터넷에 노출하면
안 되고, 차량 수천 대에 Kafka ACL을 발급·폐기하는 것도 현실적이지 않다. 앞서 "차량이
Kafka 클라이언트를 직접 돌릴지"를 검토했는데, 그건 이 층을 건너뛰자는 것이라 **기각한다.**

### 판단 기준 — 결정력 순서

| 순위 | 기준 | 우리 답 |
|---|---|---|
| 1 | **신뢰 경계를 넘는가** | 넘는다 → 업링크와 내부 버스 분리, 게이트웨이 필요 |
| 2 | **핵심 주장이 무엇에 의존하는가** | 오프셋 재생 → **Kafka** (아래) |
| 3 | **레이트가 프로토콜 한계에 걸리는가** | 걸린다 → 고주파는 **gRPC** (§4.1) |
| 4 | 관리형 vs 자체호스팅 | 자체호스팅 — 브로커 HA를 실증했다 |
| 5 | 커넥터 성숙도 | Flink↔Kafka가 가장 성숙 |

**1~3은 기술적 강제이고 4~5에서만 선택이 개입한다.**

## 4.7 ⚠️ "왜 Kafka인가"의 근거가 문서에서 사라졌다

v2.0에 `ADR-002: 수집 = Kafka self-host (vs Pub/Sub)`가 있었는데 v3.0 재작성 때 유실됐다.
지금 문서에 Pub/Sub 기각 근거가 없다. 채운다.

| | **Kafka (채택)** | GCP Pub/Sub |
|---|---|---|
| 모델 | **오프셋 있는 파티션 로그** | ack 기반 메시지 큐 |
| 재생 | 오프셋으로 임의 지점 되감기 | 타임스탬프 seek · 스냅샷 |
| **Flink exactly-once** | 컨슈머 오프셋을 **체크포인트에 저장**해 정확한 지점 재탐색 | 오프셋 개념이 없어 같은 방식 불가 |
| 순서 | 파티션 키 단위 보장 | ordering key (제약 있음) |
| 생태계 | Flink·Kafka Connect·Debezium 1급 | GCP 네이티브 |

**기각 이유**: Flink의 exactly-once는 **"컨슈머 오프셋을 체크포인트에 넣고 실패 시 그 지점으로
재탐색"** 으로 성립한다. Pub/Sub은 오프셋이 없어 이 방식이 안 된다. 참고로 Pub/Sub→Kafka
소스 커넥터조차 **at-least-once만 보장**하고 재시작 시 중복이 생긴다.

**이 프로젝트의 핵심 주장이 "유실 0·중복 0 증명"이므로 Kafka는 취향이 아니라 요구사항에서
도출된다.** Pub/Sub을 쓰면 논지가 약해진다.

**Pub/Sub이 옳았을 경우**: GCP 네이티브 스택에서 운영 부담을 최소화하는 것이 목표이고
exactly-once를 애플리케이션 수준 멱등성으로 대신할 수 있다면 맞다. 우리 요구에 안 맞는다.

## 4.8 최종 판단 — gRPC(고주파) + MQTT(저주파) + WAL

§4.1에서 "MQTT가 틀렸다"고 결론냈으나, MQTT의 이점(QoS1 무료 ack·LWT·오프라인 버퍼)을
포기하는 것이 맞는지 재검토했다. 판단 기준은 **목적 두 가지**다.

> **① 센서 데이터를 유실 없이 안전하게 처리한다**
> **② 차량 수가 늘어날 수 있는 확장성 있는 설계**

앞서 강조했던 "처리량 문제의 가시성"은 목적이 아니므로 판단에서 제외한다.

### 4.8.1 먼저 얽힌 것을 푼다 — 배치와 프로토콜은 별개 결정이다

| | |
|---|---|
| **결정 1** | 배치를 **데이터 계약**에 넣을지 |
| **결정 2** | 프로토콜 |

MQTT는 프로토콜 배치가 없어 **결정 1을 강제**한다. 그래서 두 결정이 묶여 보였다.
gRPC는 둘 다 가능하다.

**그리고 배치의 확장성 이점(메시지 수 감소)은 전송 계층 배치로도 얻는다.**

```
gRPC 레코드 단위 → 게이트웨이 → Kafka 프로듀서(linger.ms) → Kafka는 배치로 받는다
```

| 1,000대 기준 | 계약 배치 (A) | 전송 배치 (B) |
|---|---|---|
| Kafka 메시지 수 | 낮음 | **동등하게 낮음** |
| 대역폭 | 432 MB/s | 432 MB/s (동일) |
| 계약 입도 | 배치 | **레코드** |

**즉 B는 버스 효율을 포기하지 않는다.** §4.1에서 "배치냐 아니냐"로 프레이밍한 것은
부정확했다 — 문제는 배치 자체가 아니라 **배치가 계약에 있는지**다.

### 4.8.2 기준 ① 유실 없음 — 닫아야 할 구멍 수

WAL은 **양쪽 다 필요하다.** 축적 창은 `publish()` 이전이라 MQTT 클라이언트의 persistent
inflight store가 덮지 못한다. 그 외에 남는 구멍:

| 구멍 | A: MQTT + 계약 배치 | B: gRPC 레코드 단위 |
|---|---|---|
| 축적 창 | WAL | WAL (배치 없어 창 자체가 작다) |
| 전송 중 손실 | ✅ **QoS1 무료** | ⚠️ **직접 구현** |
| 브로커 persistence 미설정 | ⚠️ **기본 꺼짐** | 브로커 없음 |
| 구독자 QoS 별개 협상 | ⚠️ 실효 QoS = min(발행, 구독) | 없음 |
| session expiry / clean start | ⚠️ inflight 스토어 소실 | 없음 |
| 브로커 큐 상한 | ⚠️ N=100에서 0.84초분 | 없음 |
| in-flight window 천장 | ⚠️ 있음 | 없음 |
| 게이트웨이/브리지 ack 순서 | ⚠️ 있음 | ⚠️ 있음 |

**A는 닫을 구멍이 5개 더 많고, B는 직접 만들 것이 1개 더 많다.**

B의 그 1개가 실질적이다 — **gRPC 스트림에는 메시지별 ack가 없다.** 스트림이 끊기면 서버가
어디까지 받았는지 모른다. ack 프로토콜을 설계해야 한다: **서버가 주기적으로 최고 수신 `seq`를
되돌려주고, 클라이언트가 그에 맞춰 WAL 커밋 포인터를 전진**시킨다. QoS1이 무료로 주는 것을
직접 만드는 것이 B의 진짜 대가다.

**다만 두 종류의 성격이 다르다.**

| | 성격 |
|---|---|
| A의 구멍 5개 | **설정 실수 하나로 조용히 유실된다.** mosquitto `persistence` 기본 꺼짐이 대표적 — PUBACK은 이미 보냈는데 브로커 재시작하면 사라지고, 퍼블리셔는 성공으로 안다 |
| B의 ack 프로토콜 | **한 번 만들면 명시적으로 검증 가능하다** |

조용히 새는 것보다 만들고 검증하는 쪽을 택한다.

### 4.8.3 기준 ② 확장성 — 여기가 결정적이다

| | A: MQTT 브로커 | B: gRPC 게이트웨이 |
|---|---|---|
| 상태 | **stateful** — 세션·구독·큐·inflight | **stateless** |
| 확장 방법 | 브로커 클러스터, **세션 상태 분산** | L4 LB 뒤에 **인스턴스 추가** |
| 장애 시 | 세션 재배치, 큐 소실 위험 | 스트림 재연결, WAL이 복구 |
| 병목 | 브로커 + 브리지(샤딩 필요) | 게이트웨이(수평) |

**MQTT 브로커는 상태를 갖는 초크포인트다.** 차량이 늘면 세션·구독·큐를 클러스터에 분산해야
하고, 그것이 MQTT 클러스터링의 어려운 부분이다.

**게이트웨이가 stateless일 수 있는 이유는 WAL이 차량에 있기 때문이다** — 재연결 시 차량이
어디부터 다시 보낼지 안다. 우연이 아니라 WAL을 두기로 한 결과이며, **확장성과 유실 방지가
같은 결정에서 나온다.**

### 4.8.4 결론

| 기준 | 판단 |
|---|---|
| **유실 없음** | B. 구멍이 5개 적고, 대신 만드는 1개는 검증 가능하다 |
| **확장성** | B. **stateless 게이트웨이**가 결정적 — 세션 분산 vs 인스턴스 추가는 운영 난이도가 다르다 |
| 버스 효율 | 동등 (전송 계층 배치) |
| MQTT 이점 | **저주파 채널에서 그대로 유지** |

**MQTT를 포기하는 것이 아니다.** 발생률로 나눠 각자 맞는 곳에 쓴다 — LWT 오프라인 검출,
오프라인 버퍼, 장래 명령 다운링크는 저주파 채널에서 그대로 얻는다.

### 4.8.5 A를 택할 조건

**A가 틀린 엔지니어링은 아니다.** 실제 텔레매틱스 스택이 그렇게 한다. 다음이면 A가 맞다.

- 차량이 임베디드·저전력이라 HTTP/2 스택이 부담된다
- ack 프로토콜을 직접 만들 여력이 없다 (QoS1로 대신한다)
- 브로커 팬아웃·retained message가 필요하다
- **차량 수 상한이 수백 대로 정해져 있다** — 브로커 클러스터링이 불필요하다

마지막 항목이 갈림길이다. **차량 수가 수천 대 이상으로 늘 수 있다는 것이 목적에 있으므로 B다.**

### 4.8.6 ⚠️ 정직하게 남는 대가

**WAL과 ack 프로토콜은 둘 다 온보드 소프트웨어**이고, [SDD §4.2](sdd.md) **L-2에
"구현하지 않는다"** 로 등재돼 있다.

즉 **"유실 없음"을 설계했지만 그 핵심 부분을 만들지 않는다.** 지금 "차량"이 같은 머신의
재생기라 실제로 문제는 생기지 않는다.

> 그래서 문서에는 **"축적 창을 닫았다"가 아니라 "닫는 방법을 설계했다"** 로 적는다.
> 이 구분이 무너지면 검증되지 않은 주장이 된다. SDD §4.2 **L-13**으로 등재한다.

## 5. 수정 후 설계

```
차량
 │
 ├─ ① 신호 1,295 rec/s ──┐
 ├─ ② 인지    2.1 msg/s ──┴─[WAL]─[gRPC 스트림, mTLS]──▶ 게이트웨이(stateless) ──▶ Kafka
 │                              레코드 단위 계약 · seq        Kafka 프로듀서 linger.ms
 │                              서버가 최고 수신 seq 반환      ack 후 WAL 커밋 전진
 │
 ├─ ③ 원시   27.15 MB/s ────[HTTPS resumable]──────────▶ 오브젝트 스토리지 (MCAP)
 │                                                            │ 업로드 완료 후
 └─ segment-ref · 상태 · heartbeat ─[MQTT 5.0, QoS1]─▶ 브로커 ─┴─▶ 브리지 ──▶ Kafka
                                     LWT 오프라인 검출
```

**바뀐 것**

| | 이전 | 수정 |
|---|---|---|
| 신호·인지 전송 | MQTT + 100ms 애플리케이션 배치 | **gRPC 스트림**, 전송 계층 배치 |
| 데이터 계약 | 배치 (`SignalBatch`) | **레코드 단위** |
| dedup 단위 | 배치 | **레코드** (`event_id`) |
| MQTT 역할 | 신호·인지 전 구간 | **저주파 채널만** (LWT 유지) |
| 유실 탐지 | 없음 | **`seq` 결번 검출** |
| durability | 없음 | **WAL** (온보드, 미구현 — §4.8.6) |
| 확장 단위 | 브로커 클러스터 | **stateless 게이트웨이** |

**dedup 상태가 다시 커진다** — [잠정 노트 §6-1](pipeline-notes-provisional.md)의 배치 단위
132배 절감이 무효다. 상태 크기를 위해 실패 입도를 희생하는 것은 잘못된 교환이었다.
레코드 단위 dedup의 상태 전략은 §6에 미결정으로 남긴다.
