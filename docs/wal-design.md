# 온보드 WAL 설계 — 축적 창을 닫는 로컬 디스크 스풀

| 항목 | 값 |
|---|---|
| 상태 | 설계 (미구현 — [SDD §4.2](sdd.md) L-2·L-13) |
| 관련 | [수집 계층 검토 §4.8](ingestion-design-review.md) · [SDD §3 S-7](sdd.md) |
| 대상 부하 | **1,295 rec/s · 433 KB/s · 38.3 GB/일** (차량 1대, [실측](data-design.md)) |

---

## 1. 개요

### 1.1 WAL이 여기서 무엇인가

차량에서 센서 레코드를 받는 즉시 **로컬 디스크에 append-only로 기록**하고, 전송은 그
기록을 읽어서 한다. 서버가 수신을 확인하면 커밋 포인터를 전진시키고, 소비된 구간은 지운다.

```
센서 → [WAL append] → 전송기가 WAL에서 읽어 발행 → 서버 ack → 커밋 포인터 전진 → 구간 삭제
         ↑ 여기서 durable
```

데이터베이스의 Write-Ahead Log와 같은 원리다. **"보내기 전에 먼저 적는다"** 가 핵심이고,
그래서 프로세스가 죽거나 전원이 끊겨도 적어둔 것은 남는다.

### 1.2 왜 필요한가 — 축적 창

전송 프로토콜의 신뢰성 보장은 **`send()`를 호출한 순간부터** 시작한다. gRPC든 MQTT QoS 1이든
같다. 그 이전, 즉 레코드가 메모리 버퍼에 머무는 구간은 **프로토콜 바깥**이다.

```
센서 → [메모리 버퍼] → send() → 네트워크 → 서버
        ↑                ↑
   프로토콜 바깥      여기서부터 보장
   프로세스 죽으면
   그냥 사라진다
```

이 구간을 **축적 창(accumulation window)** 이라 부른다. WAL은 축적 창을 닫는 **유일한**
방법이다 — 재전송으로는 애초에 존재를 모르는 것을 되살릴 수 없다.

> MQTT 클라이언트의 persistent inflight store(Paho의 파일 persistence 등)는 **`publish()`
> 이후**를 덮는다. 축적 창은 그 이전이므로 클라이언트 스토어로는 닫히지 않는다.
> **프로토콜 선택과 무관하게 WAL이 필요한 이유다.**

### 1.3 어디에 있는가

```
차량(온보드)                             클라우드
┌──────────────────────────┐
│ 센서 → WAL → 전송기 ─────┼─[gRPC]─▶ 게이트웨이(stateless) ─▶ Kafka
│         ▲       │        │              │
│         └───────┘        │              └─ 최고 수신 seq 반환
│      ack 후 커밋 전진     │
└──────────────────────────┘
```

**게이트웨이가 stateless일 수 있는 이유가 이 WAL이다.** 재연결 시 어디부터 다시 보낼지
차량이 알기 때문에 서버가 세션 상태를 들고 있을 필요가 없다. 유실 방지와 확장성이 같은
결정에서 나온다.

## 2. 핵심 요구사항 및 문제상황

### 2.1 요구사항

| ID | 요구사항 |
|---|---|
| **W-1** | 레코드가 전송되기 전에 **durable**해야 한다 (프로세스 종료·전원 손실 모두) |
| **W-2** | 재시작 시 **보내지 않은 지점부터 재개**해야 한다 |
| **W-3** | 디스크 사용량이 **유한**해야 한다 |
| **W-4** | 쓰기 부하 433 KB/s를 **처리 지연 없이** 흡수해야 한다 |
| **W-5** | 유실이 발생하면 **탐지 가능**해야 한다 ([L-12](sdd.md)) |
| **W-6** | 크래시 직후 **손상된 꼬리를 복구**할 수 있어야 한다 |

### 2.2 문제상황

#### P-W1. fsync 없이는 전원 손실을 못 막는다

프로세스가 죽는 것과 전원이 끊기는 것은 다르다.

| | 페이지 캐시만 (fsync 없음) | fsync |
|---|---|---|
| 프로세스 종료 | ✅ 살아남는다 (커널이 들고 있다) | ✅ |
| **전원 손실** | ❌ **사라진다** | ✅ |

**차량은 전원이 끊긴다.** 시동을 끄고, 배터리를 분리하고, 사고가 난다. 그러므로 fsync가
필요한데, 레코드마다 fsync하면 **초당 1,295회**다. 자동차용 eMMC에서는 처리량이 무너진다.

#### P-W2. 그룹 커밋은 유실 창을 다시 만든다

fsync를 묶으면(그룹 커밋) 처리량은 살지만 **묶는 구간만큼 전원 손실 노출이 남는다.**

| 커밋 주기 | fsync/s | 회당 크기 | **전원 손실 시 유실** |
|---|---|---|---|
| 1 ms | 1,000 | 0.4 KB | 1 레코드 |
| 5 ms | 200 | 2.2 KB | 6 레코드 |
| **10 ms** | **100** | **4.3 KB** | **13 레코드** |
| 50 ms | 20 | 21.6 KB | 65 레코드 |
| 100 ms | 10 | 43.3 KB | 130 레코드 |

**축적 창이 사라지는 게 아니라 100ms에서 10ms로 줄어드는 것이다.** 이건 정직하게 말해야 한다.

#### P-W3. ⚠️ 플래시 내구성이 예상 못한 제약이다

차량 저장장치는 보통 eMMC/UFS이고 쓰기 횟수 한계가 있다.

```
하루 쓰기          38.3 GB
5년 누적           69.8 TB
32GB eMMC 내구     ≈ 96 TB  (3,000 P/E 기준)
쓰기 증폭 2~4× 감안 → 내구의 146~291%
```

**5년을 못 버틴다.** WAL이 소프트웨어 설계 문제인 줄 알았는데 **하드웨어 비용을 만든다.**

완화 선택지:

| 방법 | 효과 | 대가 |
|---|---|---|
| 용량을 키운다 (256GB UFS ≈ 768 TB 내구) | 해결 | 하드웨어 비용 |
| 산업용 등급(SLC/pSLC) | 해결 | 비용 더 큼 |
| **채널별 차등 durability** | 쓰기 72% 감소 | **무손실 원칙 훼손** |
| 다운샘플 | 근본 해결 | 무손실 원칙 포기 |

세 번째가 흥미롭다 — `zoesensors`(937Hz)가 전체 레코드의 **72%** 인데, 밀리초 이하로 뽑히는
페달 센서 샘플 하나하나가 durable 저장을 받아야 하는지는 **활용처가 정해진 뒤에야 답할 수
있다.** 현재는 미결정으로 남긴다.

#### P-W4. 디스크가 유한하므로 backpressure는 어디론가 가야 한다

네트워크가 오래 끊기면 WAL이 자란다. 상한에 닿으면 둘 중 하나다.

| 선택 | 결과 |
|---|---|
| 오래된 것을 버린다 | **명시적 유실** (하지만 탐지 가능) |
| 쓰기를 막는다 | 센서 계층으로 역전파 → **드라이버 링버퍼 오버런** (탐지 불가) |

**WAL은 이 선택을 없애주지 않는다.** 유실 지점을 밀리초에서 시간 단위로 미루는 것이다.

| 용량 | 버티는 시간 |
|---|---|
| 1 GB | 0.6 시간 |
| **10 GB** | **6.3 시간** |
| 50 GB | 31.4 시간 |
| 100 GB | 62.7 시간 |

#### P-W5. 크래시 시점의 꼬리가 손상된다

쓰기 도중 죽으면 마지막 레코드가 잘린 채 남는다. 그대로 읽으면 파싱 오류나 쓰레기 데이터가
된다. **복구 시 유효한 지점까지 잘라내야 한다.**

## 3. 해결방법 및 구현 방식

### 3.1 레코드 포맷 — 길이 접두 + CRC

```
┌────────┬─────────┬────────┬──────────────┐
│ len:4  │ crc32:4 │ seq:8  │ payload:len  │
└────────┴─────────┴────────┴──────────────┘
```

| 필드 | 역할 |
|---|---|
| `len` | 다음 레코드 경계. 이것 없이는 순차 스캔이 안 된다 |
| `crc32` | **P-W5 해결** — 잘린/손상된 레코드를 판별한다 |
| `seq` | 차량별 단조 순번. **P-W5(복구 지점)와 W-5(유실 탐지)를 동시에 해결** |
| `payload` | 직렬화된 레코드 |

**`seq`를 WAL에서 발급하는 것이 중요하다.** WAL append가 레코드가 **처음으로 durable해지고
순서가 확정되는 지점**이기 때문이다. 여기보다 앞에서 발급하면 순서가 흔들리고, 뒤에서
발급하면 재시작 후 연속성이 깨진다.

`event_id`(ULID)와 역할이 다르다 — `event_id`는 **멱등성**(같은 것을 두 번 처리하지 않음),
`seq`는 **연속성**(빠진 것을 알아냄).

### 3.2 세그먼트 롤링 — 단일 파일이 아니다

```
wal/
├── 000000000000.seg   (닫힘, 커밋 완료 → 삭제 대상)
├── 000000001024.seg   (닫힘, 전송 중)
└── 000000002048.seg   (활성, append 중)
```

**왜 세그먼트인가** — 커밋된 구간을 지울 때 **파일을 통째로 삭제**하면 되기 때문이다.
단일 파일이면 앞부분을 잘라내야 하는데, 그건 파일 재작성이거나 sparse file 트릭이 필요하고
둘 다 복잡하다.

세그먼트 크기는 **64 MB** 정도가 적당하다 — 433 KB/s에서 약 150초분이다. 너무 작으면 파일
개수가 폭증하고, 너무 크면 삭제 단위가 커져 디스크 회수가 늦다.

### 3.3 그룹 커밋 — fsync 정책

```
append(record)          → 버퍼에 쓰고 즉시 반환 (센서를 막지 않는다)
매 10ms 또는 4KB마다    → write() + fsync()
                        → 그 지점까지 durable로 표시
```

**10ms를 제안한다** (P-W2 표). 전원 손실 시 최대 13 레코드를 잃고 fsync는 초당 100회다.
1ms로 줄이면 fsync가 초당 1,000회가 되어 eMMC에서 버티지 못하고, 100ms로 늘리면 유실이
130 레코드로 커진다.

**센서 콜백을 절대 막지 않는다.** append는 메모리 버퍼에 쓰고 바로 반환하고, fsync는 별도
스레드가 한다. 막으면 드라이버 링버퍼 오버런(P-W4의 나쁜 선택지)이 된다.

### 3.4 커밋 포인터 — 정밀할 필요가 없다

```
wal/COMMIT   →  { segment_id, offset, seq }
```

서버가 반환한 최고 수신 `seq`를 받아 전진시키고, 주기적으로(예: 1초) fsync한다.

**레코드 단위 정밀도가 필요 없는 이유** — 커밋 포인터가 뒤처져 있으면 재시작 후 **이미 보낸
것을 다시 보낸다.** 그건 중복이고, 하류의 `event_id` dedup이 흡수한다.

> **WAL은 at-least-once면 충분하다.** exactly-once를 WAL에서 만들려 하면 복잡해지는데,
> 이미 dedup 계층이 있으므로 그럴 필요가 없다. 계층별 책임 분리다.

### 3.5 복구 절차

```
1. COMMIT 파일을 읽어 (segment_id, offset, seq) 확보
2. 그 세그먼트의 offset부터 순차 스캔
3. 레코드마다 len 읽고 → crc32 검증
     통과: 다음으로
     실패 또는 len이 남은 바이트보다 큼: **여기가 손상된 꼬리** → 이 지점에서 truncate
4. 유효한 마지막 seq를 확인 → 전송기가 여기부터 재개
5. COMMIT보다 앞선 세그먼트는 삭제
```

3번이 P-W5를 닫는다. **CRC 실패를 오류로 보지 않고 "꼬리를 찾았다"로 해석**하는 것이 요점이다.

### 3.6 backpressure 정책 — 명시적으로 고른다

```
디스크 사용량 < 80%   →  정상 append
80% ~ 95%            →  경고 지표 발행 + 전송 우선순위 상향
> 95%                →  정책 적용
```

**정책은 "오래된 세그먼트 삭제"를 택한다.** 근거:

| | 오래된 것 삭제 | 쓰기 차단 |
|---|---|---|
| 유실 위치 | WAL (우리 코드) | 드라이버 링버퍼 (프로토콜 바깥) |
| **탐지 가능?** | ✅ `seq` 결번으로 | ❌ **조용히 사라진다** |
| 최신 데이터 | 유지 | 유실 |

**관제에서는 최신 상태가 과거보다 중요하고, 무엇보다 탐지 가능한 유실이 조용한 유실보다
낫다.** 삭제할 때는 삭제한 `seq` 구간을 별도로 기록해 나중에 대사할 수 있게 한다.

### 3.7 전송기와의 인터페이스

```
read_from(seq) -> Iterator[Record]     # 커밋 포인터부터 순차 읽기
commit(seq)                            # 서버 ack 반영
stats() -> { pending_bytes, pending_records, oldest_seq, disk_pct }
```

`stats()`가 관측 지표로 나간다 — **WAL 적체량이 곧 "네트워크가 못 따라가고 있다"의 지표**다.
[SDD §6.2](sdd.md)에 추가해야 한다(현재 없다).

### 3.8 구현 순서

| 단계 | 내용 | 검증 |
|---|---|---|
| 1 | 레코드 포맷 + append/scan | 라운드트립 테스트, 손상 꼬리 주입 |
| 2 | 세그먼트 롤링 + 삭제 | 용량 상한 준수 |
| 3 | 그룹 커밋 fsync | fsync 횟수·지연 측정 |
| 4 | 커밋 포인터 + 복구 | **프로세스 강제 종료(SIGKILL) 후 재개** |
| 5 | backpressure 정책 | 디스크 채우고 `seq` 결번 확인 |

**4번이 핵심 검증이다.** 임의 시점에 SIGKILL하고, 재시작 후 `seq` 결번이 없는지(중복은 허용)
확인한다. 이게 통과하면 W-1·W-2·W-6이 실증된다.

## 3.9 중량 경로의 outbox로도 쓴다

WAL은 **Transactional Outbox와 구조가 같다** — durable 중간 저장소 + 릴레이 + 발행 확인 후
포인터 전진. 둘 다 at-least-once이고 하류 dedup이 필요하다.

다만 **원래 푸는 문제가 다르다.**

| | Transactional Outbox | 온보드 WAL |
|---|---|---|
| 푸는 문제 | **dual-write** — DB 갱신과 이벤트 발행의 원자성 | **축적 창** — 전송 전 durability |
| 원자적일 대상 | 비즈니스 트랜잭션 | 없다 |
| 저장소 | 보통 같은 RDB의 테이블 | append-only 파일 |
| 쓰기 부하 | DB 트랜잭션 | 순차 append |

Outbox가 테이블을 쓰는 것은 **트랜잭션에 참여해야 하기 때문**이다. 우리는 그 제약이 없어
파일을 쓸 수 있고, 1,295 rec/s를 RDB 트랜잭션으로 받으면 그 자체가 병목이 된다.

### 그런데 중량 경로에는 진짜 dual-write가 있다

[SDD §1.4](sdd.md)는 중량 경로에 **"업로드 완료 후에 참조를 발행한다"** 는 순서 계약을 뒀다.
그런데 **순서만으로는 한쪽 실패만 막힌다.**

```
① MCAP 업로드 성공
②      ← 여기서 프로세스가 죽으면
③ segment-ref 발행

결과: 파일은 있는데 카탈로그에 없다 = 고아 파일
```

두 시스템(오브젝트 스토리지 + 메시지 버스)의 일관성 문제이므로 **정확히 dual-write이고,
outbox가 표준 해법이다.** 그리고 **WAL이 그 outbox 역할을 그대로 한다.**

```
1. MCAP 업로드 (HTTPS resumable)
2. 성공 시 → segment-ref 를 **WAL에 append**   ← 여기서 durable
3. 전송기가 WAL에서 읽어 발행
4. ack 후 커밋 포인터 전진
```

2번이 durable하므로 3번 전에 죽어도 재시작 후 발행된다. **고아 파일이 생기지 않는다.**

**WAL 하나가 두 역할을 겸한다** — 경량 경로의 축적 창 방지 + 중량 경로의 outbox.
레코드 포맷에 종류 구분(`kind`)만 추가하면 같은 로그를 공유할 수 있다.

역방향 고아(카탈로그에 있는데 파일이 없음)는 순서 계약만으로 이미 막힌다. 그리고 `checksum`이
참조에 실려 있으므로 소비자가 무결성을 검증할 수 있다.

| 실패 모드 | 순서 계약만 | **+ outbox** |
|---|---|---|
| 발행 후 업로드 실패 | ✅ 막힘 (순서) | ✅ |
| **업로드 후 발행 전 사망** | ❌ **고아 파일** | ✅ 재시작 후 발행 |
| 업로드 파일 손상 | `checksum`으로 탐지 | ✅ |

## 4. 한계

| # | 한계 |
|---|---|
| **구현하지 않는다** | 온보드 소프트웨어이므로 [SDD](sdd.md) L-2·L-13 범위 밖이다. **"축적 창을 닫았다"가 아니라 "닫는 방법을 설계했다"** 가 정확한 표현이다 |
| 전원 손실 창이 남는다 | 그룹 커밋 10ms → 최대 13 레코드. 0이 아니다 |
| 플래시 내구성 | 5년 누적이 32GB eMMC 내구를 초과한다(P-W3). 하드웨어 선택 또는 차등 durability가 필요하다 |
| 레코드 종류 구분 미결정 | 경량 레코드와 `segment-ref`를 같은 WAL에 담으려면 `kind` 필드가 필요하다(§3.9). 포맷 확정 시 반영 |
| 채널별 차등 durability 미결정 | `zoesensors` 937Hz가 쓰기의 72%인데 durable 저장이 필요한지 미정 |
| 디스크 상한 초과 시 유실 | 정책적으로 오래된 것을 버린다. 탐지는 가능하지만 유실은 유실이다 |

## 5. 재생기에서 부분 구현할 수 있다

지금 "차량"은 같은 머신의 재생기이므로 WAL이 실제로 필요하지 않다. 다만 **재생기에 단순화된
WAL을 넣으면 설계를 실증할 수 있다** — 특히 §3.8의 4번(SIGKILL 후 재개)은 로컬에서 그대로
검증된다.

그러면 L-13이 "설계했지만 안 만들었다"에서 **"재생기에서 검증했다, 실차량에는 없다"** 로
바뀐다. 주장의 강도가 달라진다.
