## 총평

전반적으로 매우 인상적인 수준의 설계 문서입니다. Medallion 아키텍처, Kappa 패턴, 폴리글랏 저장소 등 현대 데이터 엔지니어링의 핵심 개념을 깊이 이해하고 있으며, 특히 각 기술 선택의 근거를 ADR(Architecture Decision Record)로 명확히 남긴 점은 시니어 수준의 설계 역량을 보여줍니다.

다만, 1인 포트폴리오의 현실적 제약(비용)을 해결하기 위해 채택한 일부 운영 모델과, 장애 복구 시나리오의 구체성, 비용 추정의 현실성 측면에서 몇 가지 중대한 약점이 발견되어 구현 전 반드시 보완이 필요합니다.

## 발견사항

### [BLOCKER] §5.4, R-4: 단일 잡 3-way 싱크의 장애 전파 및 불명확한 복구 경로

*   **근거**: 설계의 핵심인 "하나의 스트림 잡, 3-way 싱크" 구조는 한 싱크(e.g., BigQuery)의 장애나 성능 저하가 워터마크 정체를 유발하여 다른 싱크(Iceberg, ES)까지 마비시키는 **강한 결합(tight coupling)**을 내포합니다. ES 장애 시 DLQ로 격리(shedding)하는 대책은 훌륭하지만, BigQuery 장애 시의 대책으로 제시된 "상한 후 배치 재적재로 전환"은 구체적인 메커니즘이 없습니다. 어떻게 스트리밍 잡이 실패를 인지하고 '배치 전환'을 트리거하는지, 그동안 누락된 데이터는 어떻게 처리하는지에 대한 설명이 부재하여, 실제 장애 발생 시 데이터 유실 또는 장시간 파이프라인 중단으로 이어질 수 있습니다. 이는 G-1(무손실), G-3(실시간 서빙) 목표를 위반할 수 있는 심각한 설계 결함입니다.
*   **수정 제안**:
    1.  **구체적인 장애 전환 패턴 명시**: BigQuery Storage Write API 쓰기 실패가 지속될 경우, 해당 PCollection을 별도의 Pub/Sub 토픽(e.g., `telemetry.bq_failed`)으로 보내는 사이드 출력을 명시하십시오. 이후 별도의 Dataflow 배치 잡(또는 Cloud Function)이 이 토픽을 읽어 BQ에 재시도하는 '비동기 백필' 패턴을 정의해야 합니다.
    2.  **싱크 분리 고려**: 비용이 민감한 것은 이해하지만, 안정성을 위해 실시간성이 가장 중요한 ES 싱크 잡과, 분석 정합성이 중요한 Iceberg/BQ 싱크 잡을 분리하는 대안을 재검토하고 ADR에 기록하십시오. 분리 시 장단점(비용 증가 vs. 장애 격리)을 명확히 비교해야 합니다.

### [MAJOR] §9.1: Dataflow 비용 추정의 심각한 과소평가

*   **근거**: 월 $15–30으로 추정한 Dataflow 비용은 vCPU/메모리 시간당 요금만 고려하고, 실제 스트리밍 비용의 상당 부분을 차지하는 **Streaming Engine의 "처리된 데이터 양(Data Processed)" 과금을 완전히 누락**했습니다. 6시간 동안 1억 건(5,000 rps)의 이벤트를 처리하고 dedup을 위해 상태를 유지/셔플링하는 과정에서 발생하는 데이터 처리 비용은 시간당 워커 비용을 상회할 수 있습니다. 이는 개인 크레딧 예산을 쉽게 초과할 수 있는 중대한 계산 착오이며, 프로덕션 비용 구조에 대한 이해 부족으로 비칠 수 있습니다.
*   **수정 제안**: GCP 요금 계산기를 사용해, 5,000 rps (이벤트당 1KB 가정 시 약 18 GB/hour) 트래픽에 대한 Dataflow Streaming Engine 데이터 처리 비용을 포함하여 비용을 재산정하십시오. 현실적인 추정치를 제시하고, 이를 바탕으로 부하 테스트의 규모나 시간을 조정하는 등 비용 통제 전략을 보다 구체화해야 합니다.

### [MAJOR] 포트폴리오 완성도: CI/CD 및 모니터링 구체성 부재

*   **근거**: IaC(Terraform), CI(GitHub Actions)는 언급되었지만, 실제 코드가 어떻게 빌드, 테스트, 배포되는지에 대한 구체적인 **CI/CD 파이프라인 설계가 전혀 없습니다.** Java 애플리케이션은 어떻게 컨테이너화 되는지, Dataflow Flex 템플릿은 어떻게 빌드 및 배포되는지, dbt와 Airflow DAG는 어떻게 테스트되고 동기화되는지 보여주지 않으면 '운영 가능한 시스템'이라는 인상을 주기 어렵습니다. 마찬가지로 §10.2 관측성 역시 개념(RED/USE)만 나열했을 뿐, "어떤 대시보드에서 어떤 메트릭을 볼 것인가" (e.g., Pub/Sub 구독 백로그, Dataflow 시스템 지연, DLQ 메시지 수, ES 색인 지연 시간 p99)에 대한 구체적인 청사진이 없습니다.
*   **수정 제안**:
    1.  `10.5 CI/CD`와 같은 섹션을 추가하여, GitHub Actions 워크플로우를 다이어그램이나 단계별 설명으로 제시하십시오. (e.g., `main 브랜치 push → Java 테스트 및 빌드 → Docker 이미지 빌드 및 GCR 푸시 → Terraform apply 실행`).
    2.  §10.2에 Grafana/Kibana 대시보드의 목업(mockup)이나 핵심 모니터링 항목 목록을 구체적으로 기술하여, 문제 발생 시 어떻게 원인을 찾아갈 것인지 보여주십시오.

### [MINOR] §6.4.1: exactly-once 주장의 미묘한 과장과 잔존 중복 리스크

*   **근거**: 문서 스스로 "Silver에 드물게 중복 잔존 가능"하다고 정직하게 밝힌 점은 훌륭합니다. 다만, `exactly-once`라는 용어는 데이터 엔지니어링에서 매우 강한 보장을 의미하므로, 이처럼 이론적 한계가 명확한 상황에서는 '효과적인 exactly-once(effectively-once)' 또는 '멱등 처리를 통한 중복 최소화'와 같이 보다 정확한 용어를 사용하는 것이 좋습니다.
*   **수정 제안**: `exactly-once`라는 표현을 사용할 때, "Dataflow 내부 및 BQ/ES 싱크 단계에서는 보장되나, 30분 이상의 파이프라인 중단 후 재처리되는 이벤트는 dedup TTL을 벗어날 수 있음"이라는 제한 조건을 항상 명시하십시오. 또한, dbt `unique` 테스트로 잔존 중복을 '검출'하는 것에서 더 나아가, 검출 시 알림(alert)을 보내고 해당 중복 데이터를 정제하는 주기적인 클린업 잡(dbt 모델)을 운영 계획에 추가하는 것을 고려해볼 수 있습니다.

### [MINOR] §18.B: Little's Law 기반 용량 추정의 과도한 단순화

*   **근거**: 이벤트당 처리 지연 시간을 0.2초로 가정한 것은 특별한 근거가 없는 추측(guess)입니다. 실제 지연 시간은 네트워크 I/O, 직렬화, 3-way 싱크의 부하 등 수많은 요인에 따라 변동하며, 이 가정이 틀릴 경우 필요한 워커 수 추정치 전체가 어긋나게 됩니다.
*   **수정 제안**: 해당 추정이 '초기 가설'임을 명확히 하고, "실제 지연 시간과 필요 워커 수는 소규모 부하 테스트를 통해 측정하여 보정해야 한다"는 점을 더 강하게 명시하십시오. 이는 결함이라기보다는, 추정의 한계를 인정하고 검증 계획으로 연결하는 성숙한 태도를 보여줄 기회입니다.

### [MINOR] §4.1, ADR-009: 로컬 Airflow와 Cloud Composer의 상태 불일치

*   **근거**: 개발용 로컬 Airflow와 데모용 Cloud Composer가 동일한 DAG 정의를 공유하지만, 메타데이터 DB는 완전히 분리되어 있습니다. 이는 DAG 실행 이력, XCom, 연결 정보 등이 동기화되지 않음을 의미합니다. 로컬에서 성공한 태스크를 Composer가 알지 못해 재실행하는 등의 혼란이 발생할 수 있습니다.
*   **수정 제안**: 이 제약사항을 ADR-009에 명시하고, "두 환경은 상태를 공유하지 않으며, Composer 세션은 독립적인 실행 환경으로 간주한다"는 운영 원칙을 명확히 하십시오.

## 강점

1.  **현실적인 제약조건 하의 실용적 설계 (ADR-004, ADR-009)**: "ES는 정본이 아닌 재구성 가능한 서빙 사본"이라고 명확히 정의하고 파괴/재생성하는 운영 모델을 세운 점, 개인 예산 제약을 해결하기 위해 로컬/클라우드 하이브리드 오케스트레이션 모델을 고안한 점은 기술적 이상과 현실적 제약 사이에서 최적의 균형점을 찾는 능력을 탁월하게 보여줍니다.
2.  **깊이 있는 기술 선택과 명확한 근거 제시 (ADR-006, §6.8)**: 단순히 기술을 나열하는 것을 넘어, ES data stream의 `_id` upsert 불가 제약을 정확히 파악하고 일반 인덱스를 선택한 점, Iceberg 파티셔닝 전략에서 small file 문제를 고려한 점 등은 해당 기술의 내부 동작까지 깊이 이해하고 있음을 증명합니다.
3.  **정직하고 체계적인 리스크 관리 (§6.4.1, §11 ADR)**: 'exactly-once'의 이론적 한계를 숨기지 않고 정직하게 인정하며, 이를 dbt 테스트로 방어하는 다층적 접근법은 매우 성숙한 태도입니다. 모든 주요 결정 과정을 ADR로 기록하고 관리하는 것은 협업 환경에서 반드시 필요한 체계적인 설계 역량을 보여주는 강력한 증거입니다.
